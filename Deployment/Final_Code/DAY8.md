### 섹션 2(체크포인트)
   
Q1. Pydantic 검증이 막아주는 잘못된 입력
paper_schemas.py의 제약 조건들이 막아줍니다:

content: min_length=1 → 빈 메시지 차단
max_new_tokens: ge=10, le=1024 → 범위 밖 토큰 수(너무 작거나 큰 값) 차단
temperature: gt=0.0, le=2.0 → 비정상 temperature(0 이하, 2 초과) 차단
messages: min_length=1 → 빈 대화 목록 차단
doc_id 필수 → 누락 시 차단
→ 잘못된 입력은 추론에 닿기 전에 422 에러로 걸러집니다.

Q2. Depends(verify_api_key)를 제거하면?
누구나 인증 없이 호출 가능 → 무단 사용
GPU/CPU 자원 소모와 비용 폭증, DoS 공격에 취약
사용자별 추적·제한 불가, 업로드한 논문 등 데이터 오·남용 위험
→ 인증이라는 1차 방어선이 사라집니다.

Q3. run_in_executor를 사용한 이유
LLM 추론은 무겁고 오래 걸리는 동기 작업 → 그냥 실행하면 이벤트 루프가 막혀 다른 요청·헬스체크까지 멈춤 (Day 3에서 본 문제)
run_in_executor로 추론을 별도 스레드풀에서 실행 → 메인 이벤트 루프는 안 막힘 → 동시 요청 처리 가능
→ 즉 "느린 추론이 서버 전체를 멈추는 것"을 방지 (비동기 논블로킹).

### 섹션 3(프로젝트 회고)

멀티턴 대화에서 인코더와 디코더의 답변이 디코더는 입력에서 출력을 생성하고, 이를 위해 인코더와 연결되어 있는 곳을 디코더라고 합니다. 그들은 단순히 입력과 출력을 연결한 곳을 디코더라고 합니다. 라고 답변함
 ----->  파이프라인 버그가 아니라 0.5B 소형 모델 + CPU의 품질 한계

Qwen2.5-0.5B는 파라미터가 5억 개뿐이라, 트랜스포머 구조 같은 전문 개념을 정확히 설명하는 추론력·지식이 부족 → "디코더는 디코더다" 같은 동어반복이 나옴
Q&A는 논문 앞부분 3000자만 컨텍스트로 넣는데, 그 안에 encoder/decoder 정의가 충분치 않으면 모델이 지어냄(환각)
temperature=0.7이라 약간의 무작위성도 더해짐

답변 품질을 올리는 방법 (난이도순)
temperature 낮추기 — Q&A는 0.3 정도로 (덜 산만하고 일관적). paper_model.py의 answer 기본값이나 요청 파라미터 조정
더 큰 모델 — Qwen2.5-1.5B-Instruct(CPU도 가능, 느림) 또는 3B. GPU(Colab)면 품질이 확 올라감
컨텍스트 개선(RAG) — 질문과 관련된 부분만 검색해 넣기 (CONTEXT_CHARS를 늘리거나 임베딩 검색 추가) → 환각 감소
프롬프트 강화 — "모르면 모른다고 답하라"를 더 강하게, "논문에 근거한 문장만"
