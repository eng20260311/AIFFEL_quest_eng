     데이터 포맷: 주로 JSON 형태로 요청(Input 데이터)과 응답(예측 결과)을 주고받음

1. 가상환경 없이 pip install 시 설치 위치와 문제점
    설치 위치: 운영체제의 전역(Global) 파이썬 환경 또는 사용자 홈 디렉토리의 전역 라이브러리 경로에 설치
    발생하는 문제점: 여러 프로젝트가 동일한 전역 공간을 공유하므로, 프로젝트마다 필요한 패키지 버전이 다를 때 버전 충돌이 발생하여 코드가 작동하지 않을 수 있음
2. pip freeze 생성 파일과 직접 작성한 requirements.txt 차이
    pip freeze: 현재 가상환경에 설치된 모든 패키지와 하위 의존성 패키지까지 정확한 버전(==)으로 명시되어 자동 생성
    직접 작성: 개발자가 프로젝트에 직접 사용한 핵심 패키지만 선별하여 최소한으로 기록하며, 버전을 생략하거나 범위(>=)로 유연하게 지정가능
3. 동료에게 프로젝트 전달 시 .venv 폴더 대신 공유할 것
   공유 항목: 패키지 목록이 기록된 requirements.txt 파일을 공유해야 함
   이유: .venv 폴더는 생성한 컴퓨터의 고유한 절대 경로와 운영체제 환경에 종속되어 있어 다른 컴퓨터에서는 정상적으로 작동하지 않으며, 파일 크기도 너무 큼

1. 모델 추론 요청에 GET이 아닌 POST를 사용하는 이유
   데이터 크기 및 제한: GET은 URL에 데이터를 담아야 하므로 크기 제한(텍스트 위주)이 있지만, POST는 이미지, 긴 텍스트 등 대용량 추론 데이터를 본문(Body)에 안정적으로 담음
   보안 및 명세: 추론에 쓰이는 민감한 입력 데이터가 URL 로그에 노출되는 것을 방지
2. 상태 코드 422는 어떤 상황에서 발생합니까?
   문법은 맞으나 처리 불가 (Unprocessable Entity): 요청 자체는 서버에 잘 도착했으나, 서버가 요구하는 데이터 형식이 아니거나 데이터 검증(Validation)을 통과하지 못했을 때 발생합니다. (예: 필수 필드 누락, 문자열 자리에 숫자가 들어온 경우 등)
3. requests.post(url, json=data)에서 json= 파라미터가 내부적으로 하는 일직렬화 (Serialization): 파이썬의 딕셔너리(data)를 JSON 문자열로 자동 변환하여 본문(Body)에 넣습니다.
    헤더 설정: 요청 헤더의 Content-Type을 application/json으로 자동으로 지정해 줍니다.
4. Python의 True는 JSON에서 어떻게 표현됩니까?
   true (소문자): JSON 표기법에 맞춰 첫 글자가 소문자인 true로 변환되어 표현

1. state_dict로 저장한 .pth 파일을 불러올 때, 모델 클래스 정의가 필요한 이유
   데이터의 한계: state_dict는 모델 구조 정보를 제외하고 각 레이어의 가중치(Weights)와 편향(Bias) 매개변수(Tensor)만 딕셔너리 형태로 저장
   뼈대 필요성: 이 가중치 데이터를 주입할 빈 모델의 네트워크 구조(뼈대)가 코드로 먼저 정의되어 있어야만 값을 정상적으로 맵핑 가능함

2. torch.jit.trace와 torch.jit.script는 각각 어떤 황에서?             torch.jit.trace: 모델 내부에 if문이나 for문 같은 조건부 제어문이 없고, 고정된 연산 흐름(정적 그래프)을 가질 때 사용 (예시 입력 데이터를 넣어 연산 경로를 추적 및 기록함)
   torch.jit.script: 모델 내부에 입력값에 따라 실행 흐름이 바뀌는 데이터 종속적인 제어문(동적 루프, 조건문)이 포함되어 있어, 파이썬 코드 자체를 분석해 컴파일해야 할 때 사용합니다.
3. ONNX의 가장 큰 장점과 선택해야 하는 상황
   가장 큰 장점: 프레임워크 독립성입니다. PyTorch, TensorFlow 등 서로 다른 프레임워크로 학습된 모델을 하나의 표준 포맷으로 통합해 줍니다.
   선택 상황: 모델을 파이썬 환경이 아닌 C++, 모바일(iOS/Android), 웹브라우저에서 실행해야 하거나, TensorRT, OpenVINO 같은 하드웨어 가속 엔진을 사용해 추론 속도를 극대화해야 할 때 선택
4. torch.onnx.export()에서 dynamic_axes를 지정하지 않으면 생길 수 있는 문제
   크기 고정 문제: 내보내기(Export)할 때 사용했던 예시 데이터(Dummy Input)의 배치 크기(Batch Size)나 이미지 해상도(정적 차원)가 모델에 그대로 고정
   추론 실패: 배포 후 실시간 서비스에서 이와 다른 배치 크기나 크기의 데이터가 입력으로 들어오면 차원 불일치(Shape Mismatch) 에러가 발생하며 추론에 실패

Q1. 모델 학습과 모델 배포의 핵심 차이를 한 문장으로 설명하세요.
    학습은 데이터를 통해 최적의 가중치를 찾아가는 과정이며, 배포는 완성된 모델을 서버에 올려 실시간 요청에 추론 결과를 반환하는 과정입니다.
Q2. "내 컴퓨터에서는 되는데" 문제의 근본 원인은 무엇입니까?
    개발 환경과 운영(배포) 환경의 OS, 파이썬 버전, 설치된 패키지 버전, 환경 변수 등이 서로 일치하지 않기 때문에 발생합니다.
Q3. 가상환경을 사용하지 않으면 어떤 문제가 발생할 수 있습니까?
    전역 공간에 패키지가 설치되어 여러 프로젝트 간 패키지 버전 충돌이 발생하고 시스템 환경이 오염됩니다.
Q4. pip freeze와 직접 작성한 requirements.txt의 용도 차이는?
    pip freeze는 현재 가상환경의 모든 의존성 패키지와 정확한 버전을 기록하는 용도이며, 직접 작성하는 파일은 프로젝트의 핵심 패키지만 선별하여 유연하게 버전을 관리하는 용도입니다.
Q5. 모델 추론 요청에 POST를 사용하는 이유는?
    이미지나 대용량 텍스트 같은 추론 데이터를 URL 제한 없이 본문(Body)에 안정적으로 담아 보내고 보안을 유지하기 위함입니다.
Q6. 상태 코드 200, 400, 500은 각각 어떤 상황을 의미합니까?
    200 (OK): 요청이 성공적으로 처리되어 정상 응답을 반환함.
    400 (Bad Request): 클라이언트의 요청 문법이나 파라미터가 잘못되어 서버가 처리할 수 없음
    500 (Internal Server Error): 서버 내부의 코드 오류나 예외가 발생하여 요청 처리에 실패함.
Q7. state_dict 방식은 왜 모델 클래스 정의가 필요합니까?
    가중치 데이터만 딕셔너리로 저장되므로, 이를 주입하여 복원할 구조(뼈대) 역할을 하는 클래스 코드가 반드시 필요합니다.
Q8. ONNX의 가장 큰 장점과, 사용해야 할 시점은?
    프레임워크 독립성이 장점이며, 파이썬 외 환경(C++, 모바일 등)에서 모델을 실행하거나 TensorRT/ONNX Runtime 등으로 추론 속도를 극대화해야 할 시점에 사용합니다
Q9. 모델 저장 전에 model.eval()을 호출해야 하는 이유는?
    Dropout이나 BatchNorm과 같이 학습과 추론 때 다르게 동작하는 레이어들을 추론(Evaluation) 모드로 고정하여, 가중치와 상태가 왜곡 없이 올바르게 평가되고 저장되도록 하기 위함입니다.
Q10. predict() 함수를 별도 모듈로 분리한 이유는 무엇입니까?
    관심사 분리(SoC)를 통해 API 서버의 라우터 코드와 모델의 순수 추론 로직을 독립시켜, 유지보수와 단위 테스트(Unit Test)를 쉽게 만들기 위함입니다.
