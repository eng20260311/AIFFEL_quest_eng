## 2. 각 섹션 체크포인트의 답변


### 섹션 1
1. 이 프로젝트의 입력과 출력은 각각 무엇입니까?
   입력은 8가지 feature:중위 소득(MedInc), 주택 연식(HouseAge), 평균 방수(AveRooms), 평균 침실 수(AveBedrms), 인구(Population), 평균 거주 인원(AveOccup) , 위도(Latitude), 경도(Longitude) 
   출력은 :중위 주택 가격
2. MNIST프로젝트와 비교했을 때 데이터 형태가 어떻게 다릅니까?
   MNIST데이터셋은 픽셀로 이루어진 이미지 데이터이고 CNN(합성곱 신경망)을 사용한다.  California Housing은 컬럼이 정해진 정형 데이터로 선형회귀, 랜덤포레스트, 그래디언트 부스팅 같은 모델이 잘 맞는다.

3. 오늘 새로 만들 3개의 파일의 이름과 역할은 무엇입니까?
   housing_model.py:ML모델 자체와 예측 과정을 담당함
   housing_schemas.py:Pydantic으로 API의 요청/응답 데이터 구조와 유효성 검사규칙을 정의함
   housing_api.py:위의 두 파일을 가져와 실제 HTTP API로 노출함
  

### 섹션 2
1. 정규화에서 학습 데이터의 통계를 테스트 데이터에도 사용하는 이유는 무엇입니까?
   데이터 누수 방지하고 학습과 추론 간 일관성이 있고 데이터 1건만 들어오는 실서비스에서도 동작함
2. 모델 가중치 외에 함께 저장해야 하는 것은 무엇이고, 왜 필요합니까?
   전처리 파라미터와 피처 정보와 모델 구조 정의 그리고 출력 후처리 정보, 메타 데이터를 저장함

3. HousingPredictor.predict()에서 피처를 self.feature_names 순서로 배열하는 이유는? 
  클라이언트가 어떤 순서로 데이터를 보내도 학습 때 정한 피처 순서와 정확히 일치시켜서, ① 모델이 각 값을 올바른 위치로 받고 ② 정규화 통계(mean/std)와도 자리가 맞도록 보장하기 위함

### 섹션 3
1. HousingRequest에서 Latitude에 ge=32, le=42 제한을 넣은 이유는?  
   입력 좌표가 모델이 학습한 영역(캘리포니아) 안에 있는지 검증하는 장치입니다. 모델의 유효한 사용 범위(domain)를 API 차원에서 강제해서, 학습 범위 밖의 신뢰할 수 없는 예측과 명백한 입력 오류를 미리 걸러냄

2. request_model.dump()는 어떤 역할을 합니까?
   검증을 마친 Pydantic 요청 객체를 일반 딕셔너리로 변환해서, 딕셔너리를 입력으로 받는 모델 추론 함수(predict)에 넘기고 응답에도 재사용하기 위한 코드입니다.

3.  run_in_executor를 사용하지 않으면 어떤 문제가 발생합니까?
    run_in_executor 없이 무거운 동기 추론을 async def 안에서 직접 실행하면, 이벤트 루프가 그 시간 동안 통째로 멈춰서 다른 모든 요청이 처리되지 못하는 병목이 생김.서버 전체가 얼어붙은 것처럼 보임

   


### 섹션 4
1. MNIST대시보드와 비교해 입력방식이 어떻게 다릅니까? 
   MNIST 대시보드는 "이미지를 업로드 → Base64 인코딩 → 전송"하는 파일 기반 입력이고, 주택 가격 대시보드는 "여러 숫자를 폼에 입력 → JSON dict로 전송"하는 정형 데이터 폼 입력입니다.

2. st.number_input()에서 min_value, max_value를 설정하는 이유는?
  value는 반드시 min_value와 max_value 사이에 있어야 합니다. 그렇지 않으면 Streamlit이 오류를 냅니다.

3. request_data딕셔너리의 키 이름이 HousingRequest 스키마 필드의 이름과 정확히 일치해야 하는 이유는?
  Pydantic은 데이터를 순서가 아닌 "필드 이름"으로 매칭하기 때문에, request_data의 키가 HousingRequest 필드명과 정확히(대소문자까지) 같아야 합니다. 다르면 ① 검증 단계에서 422 오류가 나고, ② 통과하더라도 추론 단계에서 features[name]이 키를 못 찾습니다.


### 섹션 5(최종 체크포인트)
   
Q1. 전처리 파라미터(mean, std)를 모델과 함께 저장하는 이유
추론 시 입력을 학습 때와 똑같이 정규화해야 하기 때문입니다. 통계가 없으면 같은 입력도 다른 값으로 변환돼 예측이 망가지고, 실서비스는 데이터가 1건씩 들어와 통계를 새로 구할 수도 없습니다.

Q2. Latitude에 ge=32, le=42를 넣은 이유
32~42는 캘리포니아의 위도 범위입니다. 모델이 캘리포니아 데이터로만 학습됐으므로, 학습 범위 밖(신뢰 불가)의 입력과 명백한 오타를 모델에 닿기 전에 422 오류로 차단하기 위함입니다.

Q3. Streamlit 입력값 이름이 Pydantic 필드명과 일치해야 하는 이유
Pydantic은 데이터를 순서가 아닌 "이름"으로 매칭하기 때문입니다. 이름이 다르면 "필수 필드 누락"으로 422 오류가 나고, 통과하더라도 추론 단계의 features[name]에서 키를 못 찾습니다.

Q4. run_in_executor를 제거하면 생기는 문제
무거운 동기 추론이 이벤트 루프를 통째로 막아, 그 시간 동안 다른 모든 요청(/health 포함)이 대기합니다. 동시 처리가 사실상 순차 처리가 되어 서버 전체가 멈춘 듯 응답이 밀립니다.

Q5. MNIST 프로젝트와 오늘 프로젝트의 가장 큰 차이
문제 유형과 데이터 형태입니다. MNIST는 이미지 기반 분류(Base64 이미지 전송 → 클래스 0~9 + 확률), 오늘은 정형 데이터 기반 회귀(숫자 8개 JSON 전송 → 가격 예측)입니다.


### 섹션 6(프로젝트 회고)


6.1 오늘 만든 것 정리
캘리포니아 주택 가격을 예측하는 end-to-end 정형 데이터 예측 서비스를 완성했다.

모델: 8개 수치 특성 → 가격(회귀)을 예측하는 PyTorch 모델을 학습하고, 가중치(.pth)와 전처리 파라미터(mean/std, feature_names)를 함께 저장.
백엔드: FastAPI로 추론 API 구축 — Pydantic 입력 검증 + run_in_executor 비동기 처리.
프론트엔드: Streamlit 입력 폼 대시보드를 만들어 API와 연결하고 결과를 시각화.
테스트: 정상 / 에러 / 동시 요청을 통합 테스트로 검증.

6.2 Day 1~4와의 연결


Day 1~2 (모델 학습/저장): PyTorch 모델 학습 → 전처리 파라미터와 함께 저장하는 재현성 개념.
Day 3 (비동기 서빙): 무거운 추론을 run_in_executor로 스레드풀에 분리해 이벤트 루프 블로킹 방지.
Day 4 (API + 대시보드): FastAPI ↔ Streamlit 연동, call_api 에러 처리 패턴.
MNIST(이미지 분류)에서 → 정형 데이터 회귀로 문제 유형을 확장하며, 입력 방식(Base64 이미지 → JSON 숫자)과 출력(클래스 → 가격)의 차이를 직접 경험.

6.3 개선할 수 있는 점
모델 메타데이터 관리: 모델 버전·학습 날짜·라이브러리 버전을 함께 기록해 재현성·호환성 확보.
입력 검증 일관성: 프론트엔드(number_input 범위)와 백엔드(Pydantic 제약)의 규칙을 한 곳에서 관리해 중복·불일치 방지.
성능/확장성: 배치 추론, 모델 캐싱, 헬스체크 고도화 등으로 동시 요청 처리 능력 향상.
운영(MLOps): 로깅·모니터링, 모델 재학습 파이프라인, 컨테이너화(Docker) 등은 이후 과정에서 심화.
