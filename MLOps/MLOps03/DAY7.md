### 섹션 2
1. 토크나이저의 encode()와 decode()는 각각 어떤 변환을 수행합니까?  
   encode(): 텍스트 → 토큰 ID 리스트(숫자). 모델이 입력받을 수 있는 형태로 변환 (사람 언어 → 숫자)
   decode(): 모델이 출력한 토큰 ID → 텍스트. 사람이 읽을 수 있는 문장으로 복원 (숫자 → 사람 언어)

2. model.generate()의 temperature 파라미터는 생성 결과에 어떤 영향을 줍니까? 
   낮게 (예: 0.1) → 확률 높은 토큰만 선택 → 보수적·일관적·반복적 응답
   높게 (예: 1.5) → 확률 분포가 평평해져 다양한 토큰 선택 → 창의적·다양하지만 엉뚱할 수 있음
   0.8 정도가 자연스러움과 다양성의 균형점으로 자주 쓰임

3. 멀티턴 대화에서 이전대화 기록을 프롬프트에 포함하는 이유는 무엇입니까?  
   GPT 같은 모델은 상태(기억)가 없는(stateless) 구조 → 매 요청을 독립적으로 처리
   이전 대화를 모르면 맥락 없는 동문서답을 해서 이전 대화 전체를 프롬프트에 함께 넣어 "지금까지 이런 대화를 했다"는 문맥을 매번 제공해야 자연스러운 멀티턴 대화가 가능


### 섹션 3

1. ChatRequest의 messages가 리스트인 이유는 무엇입니까?
    대화는 여러 개의 메시지(turn)가 순서대로 쌓인 것이라서 단일 문자열이 아니라 순서 있는 목록으로 표현해야 하기 떄문임
    각 항목이 {role, content} 구조라 누가(user/bot) 무슨 말을 했는지 구분 가능

2. 서버가 대화 기록을 저장하지 않고 클라이언트가 매번 전체 기록을 보내는 이유는?  
   REST의 무상태(stateless) 원칙 — 각 요청은 독립적이고, 서버는 이전 요청을 기억하지 않음
   서버가 상태를 안 가지면 확장(scale-out)이 쉬움 — 요청이 어느 서버로 가도 동일하게 처리 (세션 공유 불필요)

3. max_new_tokens을 너무  크게 설정하면 어떤 문제가 발생할 수 있습니까? 
   생성 시간·지연 증가 — 토큰을 하나씩 순차 생성하므로 길수록 느려짐 (타임아웃 위험)
   메모리·연산 비용 증가하고 모델 최대 길이 초과 가능 → 오래된 대화가 잘리거나 오류
   불필요하게 길고 장황·반복적인 응답 생성


### 섹션 4
1. st.chat_message와 st.chat_input은 각각 어떤 역할을 합니까?
   st.chat_message(role): 채팅 말풍선(메시지 표시) 컴포넌트. user/assistant 역할별로 대화를 화면에 출력
   st.chat_input(): 화면 하단의 채팅 입력란. 사용자가 메시지를 입력하고 엔터로 전송

2. st.session_state["chat_messages"]에 대화 기록을 저장하는 이유는?   
   Streamlit은 버튼 클릭·입력마다 스크립트를 처음부터 다시 실행(rerun)함 → 일반 변수는 매번    초기화됨
   st.session_state는 재실행 사이에도 값이 유지되는 저장소
   여기에 대화를 누적해야 이전 대화가 사라지지 않고, 멀티턴 기록을 API에 보낼 수 있음

3. "대화 초기화"버튼이 st.rerun()을 호출하는 이유는 무엇입니까?
   버튼으로 chat_messages를 비워도, 화면은 이미 그려진 뒤라 즉시 반영되지 않음
   st.rerun()으로 스크립트를 강제로 다시 실행 → 비워진 상태로 화면을 새로 그려 대화가 즉시 사라지게 함

### 섹션 5
1. 챗봇 API에서 인증이 실패하면 서버는 어떤 상태 코드를 반환합니까? 
   401 (Unauthorized) — "인증 자격 증명이 없거나 잘못됨"

2. UI의 call_chat_api()는 401 응답을 받으면 사용자에게 무엇을 보여줍니까?  
    st.error()로 "🔑 인증 실패. API Key를 확인하세요." 메시지를 화면에 표시하고
     None을 반환해 응답 생성 단계로 넘어가지 않음

3. Day6의 인증 모듈(app/auth.py)을 Day7에서 수정 없이 재사용할 수 있는 이유는 무엇입니까?
   인증은 요청 데이터 내용과 무관하게 API Key 헤더만 검사하기 때문
   FastAPI의 Depends(verify_api_key) 로 엔드포인트와 느슨하게 결합(decoupling) → 어떤 엔드포인트에도 그대로 붙임
   Day 6은 이미지(UploadFile), Day 7은 텍스트(JSON)로 입력 형식만 바뀌었을 뿐 인증 로직은 동일 → 코드 변경 불필요

### 섹션 6(최종 체크포인트)
   
Q1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리 방식의 차이는?
    정형 데이터 전처리: 결측치 처리, 스케일링(정규화/표준화), 범주형 변수 인코딩(원-핫 인코딩 등)을 통해 숫자 행렬 형태로 변환합니다.
    텍스트 생성 전처리: 문자열 데이터를 토큰화(Tokenization)하고, 정수 인덱스로 변환(Embedding)한 후, 문장 길이를 맞추는 패딩(Padding) 작업을 수행합니다.
    
Q2. 멀티턴 대화에서 서버가 상태를 유지하지 않는 이유는?
    서버 확장성(Scalability): 서버가 상태를 저장하지 않으면(Stateless) 어떤 서버든 요청을 처리할 수 있어 트래픽 분산과 수평 확장이 유리합니다.
    자원 절약 및 안정성: 수많은 사용자의 대화 기록을 서버 메모리에 상주시키면 자원 소모가 크고, 서버가 다운될 때 데이터가 유실될 위험이 있습니다. 대화 기록은 주로 클라이언트가 매번 보내거나 외부 데이터베이스(DB)에서 관리합니다.
    
Q3. API Key가 잘못되면 서버는 어떤 상태 코드를 반환하고, UI는 어떻게 처리합니까?
    HTTP 상태 코드: 401 Unauthorized (미인증) 코드를 반환합니다.
    UI 처리 방식: 사용자에게 "올바르지 않은 API 키입니다"라는 에러 메시지(알림창)를 보여주고, API 키 입력 화면이나 설정 페이지로 이동하여 재입력을 유도합니다.
    
Q4. temperature를 낮추면 생성 결과에 어떤 변화가 있습니까?
    일관성 증가: 모델이 확률이 가장 높은 단어 위주로 선택하므로, 결과가 매우 결정론적(Deterministic)이고 일관되게 변합니다.
    창의성 감소: 무작위성(Randomness)이 줄어들어 답변이 정확하고 명확해지지만, 다소 딱딱하거나 반복적이고 창의성이 부족한 답변이 나옵니다.
    
Q5. 이 서비스를 다른 컴퓨터에서 실행하려면 무엇이 필요합니까?
    소스 코드: 실행할 프로그램의 스크립트 파일이 필요합니다.
    런타임 환경: 동일한 버전의 개발 언어 환경(예: Python 등)이 설치되어야 합니다.
    의존성 패키지: 프로젝트에 사용된 라이브러리 설치 파일(requirements.txt 또는 package.json 등)과 설치 과정이 필요합니다.
    환경 변수 및 API Key: 서비스 작동에 필요한 API 키나 환경 설정 값이 담긴 파일(.env 등)을 새 컴퓨터에 맞게 세팅해야 합니다.





### 회고
<어려웠던 점과 해결 과정>>
처음엔 matplotlib, transformers 등 패키지가 가상환경에 없어 설치부터 했고, GPU가 없는 환경(내장 그래픽)이라 큰 모델 대신 작은 모델로 자동 전환되는 코드 구조도 이해하게 됐다.
챗봇 API가 계속 500 에러를 내며 KeyError: 'response'가 떴는데, 알고 보니 새로 설치한 transformers 최신 버전에서 apply_chat_template의 반환 형식이 바뀐(텐서 → 딕셔너리) 호환성 문제였다. return_dict=False 옵션을 추가해 해결했다.
그런데도 에러가 계속되어서 헤맸는데, 원인은 이전에 띄워둔 서버 프로세스가 포트를 계속 점유하고 있었기 때문이었다. 코드를 고쳐도 옛 코드가 메모리에 살아있으면 반영되지 않는다는 것, 그리고 파일을 수정하면 커널을 완전히 재시작해야 한다는 점을 확실히 배웠다.
<느낀 점 / 개선할 점>
코드 자체보다 버전 호환성, 포트 충돌, 캐시된 모듈 같은 "환경 문제"가 실무에서 더 까다롭다는 걸 느꼈다. 에러 메시지를 표면만 보지 않고 실제 서버 응답(detail)까지 추적해 원인을 좁혀가는 디버깅 습관이 중요하다는 것도 배웠다.
