### chap1 체크포인트

1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇이며, 이 차이가 왜 전혀 다른 개발·테스트·운영 전략을     요구하는지 설명할 수 있으신가요?
>>Software 1.0 (명시적 코드): 사람이 직접 조건문(If-Else)과 로직을 작성하여 시스템을 구축합니다.
>>Software 2.0 (데이터 기반 코드): 사람은 목표(데이터와 정답)만 제공하고, 컴퓨터가 가중치(Weights)라는 최적의 로직을 스스로 찾아내게 만듭니다. (안드레 카파시 정의)

2. CACE 현상(Changing Anything Changes Everything)이 전통적인 소프트웨어에서는 왜 덜 문제가 되고, ML 시스템에서는  왜 치명적인지 정리해 보셨나요?
>>전통적인 소프트웨어 (Software 1.0):덜 치명적인 이유: 모듈화(Modularization)와 캡슐화가 가능합니다. A 모듈의 내부 코드를 수정해도 입력/출력 인터페이스만 유지된다면 B 모듈에 전혀 영향을 주지 않습니다.
>>ML 시스템 (Software 2.0):치명적인 이유: 모든 요소가 얽혀 있기 때문입니다. 입력 피처 하나를 수정하거나, 하이퍼파라미터를 미세하게 조정하거나, 데이터 분포가 미세하게 바뀌면 고차원 공간의 가중치 전체가 요동칩니다. 즉, 일부를 바꾸면 전체 시스템의 예측 결과가 완전히 바뀌는 현상(CACE)이 발생합니다.
>>대응 전략:이를 방지하기 위해 엄격한 데이터 버전 관리(DVC) 및 피처의 재사용성을 통제하는 피처 스토어(Feature Store) 도입이 필수적입니다;; DVC (데이터/모델 버전 관리), Feast (피처 스토어)

3. "기술의 범용화(Commoditization)"가 ML 엔지니어의 역할을 어떻게 변화시키고 있는지 자신의 언어로 설명할 수   있으신가요?
>>과거의 ML 엔지니어 (모델 중심):직접 CNN, RNN 등 복잡한 신경망 아키텍처를 처음부터 설계하고 구현하는 연구 중심의 역할이었습니다.
>>현재·미래의 ML 엔지니어 (시스템 및 가치 중심):대규모 기반 모델(Foundation Model)과 클라우드 API의 등장으로 '모델을 만드는 비용'이 극도로 낮아졌습니다.따라서 모델 자체를 짜는 것보다 "기존 거대 모델을 어떻게 우리 비즈니스에 맞게 파이프라인(RAG, Fine-tuning 등)으로 엮을 것인가", "서빙 비용을 어떻게 최적화할 것인가", "안정적인 데이터 선순환 구조를 만들 것인가"를 고민하는 시스템 통합자 및 MLOps 설계자로 역할이 이동하고 있습니다.

2.  Build vs. Buy vs. API 의사결정 트리에서, "API로 충분한가?"라는 질문에 답하기 위해 구체적으로 무엇을 확인해야   하는지 정리할 수 있으신가요?
 >>>"API로 충분한가?"에 통과(Yes)하려면 다음 4가지 핵심 체크리스트를 반드시 만족해야 합니다. 하나라도 통과하지 못하면 Buy(솔루션 구매)나 Build(자체 개발)를 고려해야 합니다.
 >>품질 및 성능 (Quality): 상용 API(예: OpenAI, Anthropic 등)가 우리가 해결하려는 도메인 문제에 충분한 정확도와 성능을 내는가?
 >>보안 및 규제 (Security & Compliance): 고객 데이터나 내부 기밀 데이터가 외부 API 서버로 전송되어도 법적·보안상 문제(개인정보보호법 등)가 없는가?
 >>비용 효율성 (Cost / ROI): 트래픽이 급증할 때 API 호출 비용(Token/Request 단위)이 자체 인프라를 구축·운영하는 비용보다 저렴한가?
 >>제어권 및 커스텀 (Control): 우리 비즈니스 특성에 맞게 모델의 행동을 미세 조정(Fine-tuning)하거나 응답 속도(Latency)를 통제해야 하는 요구사항이 적은가?

### chap3 체크포인트

1. ML 프로젝트 라이프사이클 4단계를 순서대로 말할 수 있으신가요? 
   >>1단계: 기획 및 스코핑 (Scoping)비즈니스 문제를 정의하고, ML 도입 시의 핵심 지표(KPI), 필요한 리소스 및 실현 가능성을 평가합니다.
   >>2단계: 데이터 준비 및 라벨링 (Data)학습에 필요한 데이터를 수집, 정제, 라벨링하고 특징점(Feature)을 추출하여 데이터의 정밀도를 높입니다.
   >>3단계: 모델링 및 학습 (Modeling)적절한 ML 알고리즘을 선택하고 오프라인에서 모델을 학습, 평가, 튜닝하며 비즈니스 기준 만족 여부를 검증합니다.
   >>4단계: 배포 및 모니터링 (Deployment & Monitoring)모델을 실서비스에 배포하여 유저 트래픽을 처리하고, 실시간 시스템 메트릭 및 데이터 드리프트를 상시 감시합니다.

2. "4단계 \(\rightarrow \) 2단계 되돌아감"이 가장 흔한 이유는 무엇이며, 이를 미리 방지하기 위해 기획 단계에서 어떤 질문을 던져야 하는지 생각해 보셨나요?
   >>되돌아가는 가장 흔한 이유 (현실 세계 데이터의 한계):학습할 때 썼던 데이터(2단계)와 실제 배포 후 유저가 입력하는 데이터(4단계)의 분포가 완전히 다른 훈련-서빙 데이터 불일치(Training-Serving Skew)나 배포 환경의 데이터 수집 파이프라인 누락(Data Bug)이 발생하기 때문입니다. 이를 방지하기 위해 기획(1단계)에서 던져야 할 핵심 질문:“실제 서비스 운영 환경에서 모델이 입력받을 실시간 데이터의 형태와 품질을 사전에 확보하여 학습 데이터셋에 그대로 반영했는가?”“배포 후 수집될 유저 피드백 데이터를 어떻게 자동으로 정제하고 검증하여 다시 모델로 피드백할 것인가?”

3. 데이터 플라이휠이 자연스럽게 형성되는 제품과 인위적으로 설계해야 하는 제품의 차이를 예시와 함께 설명할 수 있으신가요?

>> 데이터 플라이휠(선순환 고리)은 제품의 핵심 가치 사슬에 따라 자연스럽게 굴러가기도 하고, 엔지니어링과 UX 기획을 통해 억지로 엮어내야 하기도 합니다.

| 구분 | 특징 | 대표적인 예시 |
|------|------|------------|
| **자연스럽게 형성되는 제품<br/>(Organic Flywheel)** | 유저가 서비스를 정상적으로 이용하는 행동 그 자체가 모델을 학습시키는 최고 품질의 라벨링 데이터로 직결되는 구조입니다. | • **유튜브 / 넷플릭스**: 유저가 영상을 클릭하고 시청(혹은 이탈)하는 행위 자체가 고품질 추천 데이터가 됨<br/>• **구글 검색**: 검색 후 특정 링크를 클릭하고 체류하는 시간이 검색 품질을 높임 |
| **인위적으로 설계해야 하는 제품<br/>(Engineered Flywheel)** | 유저의 일반적인 이용 행동만으로는 AI 개선용 데이터를 얻기 어려워, UX적 장치나 유도 프로세스를 의도적으로 설계해야 하는 구조입니다. | • **B2B 의료 AI (엑스레이 판독)**: 의사가 단순히 사진만 보면 데이터가 안 쌓이므로, 판독이 틀렸을 때 수정 의견을 쉽게 제출할 수 있는 피드백 UI를 인위적으로 설계해야 함<br/>• **자율주행 (테슬라 섀도우 모드)**: 자율주행 중 인간 운전자가 핸들을 꺾어 개입(Intervention)하는 순간을 에러 데이터로 간주해 자동 수집하도록 시스템을 설계함 |

>>Human-in-the-loop (인간 개입형 시스템): AI 의료 영상 판독 보조 도구 (예: 루닛, 뷰노) 또는 AI 법률 문서 초안 작성기

>>Autonomous (완전 자율형 시스템): 테슬라의 완전자율주행(FSD) 또는 고빈도 알고리즘 주식 매매 시스템(HFT)
>>>특징: 인간의 실시간 개입이나 최종 승인 없이, AI가 인지부터 판단, 제어까지 실시간으로 완전히 독립적으로 수행합니다.

2. 하나의 제품이 처음에는 Human-in-the-loop으로 시작하여 Autonomous로 진화하는 경로를 구체적으로 그려볼 수 있으신가요? 전환의 조건은 무엇일까요?대부분의 고위험·고부가 AI 제품은 리스크를 줄이기 위해 단계적 진화 경로를 밟습니다.mermaidgraph LR
    A[Phase 1: Human-in-the-loop] -- "전환 조건 달성" --> B[Phase 2: Autonomous]
    A -.->|AI 제안 -> 인간 승인/데이터 축적| A
    B -.->|엣지 케이스 발생 시에만 인간 개입| B
>>구체적 진화 경로 예시 
    (AI 고객 상담 챗봇):초기 (Human-in-the-loop): AI가 고객 질문에 맞는 답변 초안을 3개 생성하면, 상담원이 이를 검토·수정하여 고객에게 발송합니다. 이 과정에서 상담원의 수정 내역이 다시 고품질 학습 데이터로 쌓입니다.
    진화 후 (Autonomous): AI의 답변 신뢰도가 극도로 높아지면 상담원 거치지 않고 고객에게 직접 실시간 매칭·발송하며, 판단이 모호한 극소수의 엣지 케이스(Edge Case)만 인간 상담원에게 토스합니다.
>>>  Autonomous 전환의 3대 조건:
    신뢰도 임계치 달성: 오프라인 및 섀도우 테스트에서 모델의 정확도/안전성이 목표 기준(예: 99.9%)을 상회할 것.
    실패 비용 제어 대책: AI가 오작동했을 때 막대한 손해를 막아줄 강력한 하드웨어/소프트웨어적 세이프가드(Fail-safe) 및 백업 로직의 존재.
    예외 감지 자동화: AI 스스로 "내가 이 문제를 풀 수 없다"고 인지하여 인간에게 즉시 주도권을 넘기는 불확실성 추정 기능의 완성.

| **데이터 플라이휠 전략** | 자연스러운 수집<br/>전문가가 AI 제안을 '수정하거나 채택하는 행동' 자체가 실시간으로 최상급 정답 라벨(Data)이 됨 | 인위적 엔지니어링 필요<br/>정상 주행 데이터는 쓸모없으므로, 시스템이 당황했거나(Disengagement) 실패한 순간만 골라내는 섀도우 모드 설계 필요 |

### **1️⃣ 파이프라인 위치 인식: 왜 이 단계인가?**

이 프로젝트는 **모델 배포 직후 → Full Stack DL → MLOps로 진행**되는 경로를 따릅니다.

- **모델 배포 단계**: "이 모델을 부동산 투자자에게 어떻게 서빙할 것인가?" 기획 필수
- **Full Stack DL 단계**: 정책 데이터 파이프라인, 실시간 부동산 가격 데이터 수집 API 연동
- **MLOps 단계**: 정책 변화 감지 시 즉시 모델 재학습 (매우 중요)

**특이점**: 정책이 비정기적으로 급변하므로, **배포 후 MLOps 자동화가 생존의 핵심**입니다.

### **2️⃣ 종합 기획: 6단계 프레임워크**

| 단계 | 질문 | 답변 |
|------|------|------|
| **(1) ML 필요성** | ML이 필요한가? | ✅ **부분적 YES**<br/>- 정책 변수의 조합이 복잡함 (금리+규제+세제 상호작용)<br/>- 규칙으로는 표현 어려움<br/>⚠️ BUT: 주택시장은 정책 외 요소도 중요 (심리, 환율, 글로벌 경제) |
| **(2) Build/Buy/API** | 어디서 가져올까? | **Buy (기초) + Build (정책 특화)**<br/>- 기초 예측 모델: AWS SageMaker, Google Vertex AI<br/>- 정책 변수 반영 엔진: 자체 개발 필수<br/>- 외부 데이터: 통계청, 한국은행 API |
| **(3) 아키타입** | 인간이 개입하나? | ✅ **Human-in-the-loop (권장)**<br/>- 소매 투자자: 앱에서 예측 자동 제시<br/>- 기관투자자: 자동 거래는 위험하므로 분석가 검토 후<br/>- 향후 성능 확증 후 Autonomous 전환 검토 |
| **(4) 실현가능성 × 임팩트** | 어느 사분면? | **1사분면 (장기 과제)** ⚠️<br/>- 임팩트: 높음 (부동산은 큰 시장)<br/>- 난이도: 높음 (정책 비정기, 외부 충격 많음)<br/>- 데이터: 충분하나 정책 변화 감지 파이프라인 필수 |
| **(5) 실패 비용 분석** | 손실은 얼마? | **False Positive (틀린 상승 예측) - 높음**<br/>- 투자자가 집을 샀는데 가격이 떨어짐<br/>- 손실: 개인당 수천만 원 ~ 수억 원<br/>- 신뢰도 추락 → 법적 책임 가능<br/><br/>**결론: Precision > Recall** (틀리면 안 됨) |
| **(6) PoC 종료 조건** | 성공의 기준? | ✅ Precision ≥ 75% (높은 신뢰도)<br/>✅ 평균 오차율 ≤ ±5% (5% 범위 내 예측)<br/>✅ 정책 변화 후 1주일 내 재학습 완료<br/>✅ 3개월 백테스트 수익률 > 무조건 보유<br/>✅ 베타 투자자 500명 이상 검증 |

### **3️⃣ 데이터 플라이휠 설계 (둥근 지구 ML)**

**순환 고리:**

1. 정부가 기준금리 0.25% 인상 (정책 변화)
   ↓
2. 모델: "서울 강남 집값은 3개월 내 2% 하락"
   ↓
3. 투자자 1,000명이 예측을 받음
   ↓
4. 실제로 3개월 뒤, 강남 집값이 2.1% 하락 (맞음!)
   ↓
5. 예측-결과 데이터 축적 → 모델 점진적 개선


**플라이휠 유형**: **Engineered Flywheel** (매우 고도의 설계 필요)

이유:
- 거래 완료까지 3개월 필요 (피드백 지연)
- 정책 변화가 불규칙적
- 고객 실거래 데이터 자동 수집 필수

**해결책:**
1. 부동산 플랫폼과 API 연동 (실거래가 수집)
2. 예측 결과 + 실제 결과 매칭 자동화

### **4️⃣ 실패 시나리오 분석**

| 실패 원인 | 가능성 | 사전 방지 방법 |
|----------|--------|--------------|
| **정책 변화 대응 실패** | **매우 높음** ⚠️⚠️⚠️ | 금리 인상 뉴스 후 1주일 내 재학습 필수<br/>→ 자동 재학습 파이프라인 필수<br/>→ 정책 변수 모니터링 자동화 |
| **투자자 신뢰 부족** | **높음** ⚠️⚠️ | "이 예측이 정확한가?" 회의적<br/>→ 초기 실명 투자자 50명 베타<br/>→ 월별 성적 공개 (정확도 리포트) |
| **시장 구조 급변** | **높음** ⚠️⚠️ | 정부 정책이 급변 (모델이 학습한 세상과 다름)<br/>→ 월 1회 시장 구조 변화 모니터링<br/>→ 정확도 5% 이상 하락 시 긴급 공지 |
| **거래량 급감** | **중간** ⚠️ | 규제 강화 → 거래량 격감<br/>→ 학습 데이터 분포 완전 변화<br/>→ 모델 폐기 가능성 |

**가장 높은 위험: 정책 비선형성 + 글로벌 충격**

예시:
PoC (2024년): 금리 1.5%, 안정적 시장 → 정확도 85%
배포 6개월 후: 환율 급등 + 미국 정책 급변 + 규제 강화
→ 시장이 비선형적으로 붕괴
→ 정확도 급락 (85% → 30%)

### **6️⃣ 최종 권장사항**

**아키타입 선택**
- ❌ Autonomous (너무 위험: 투자자가 자동 거래 후 손해 시 법적 책임)
- ✅ **Human-in-the-loop** (권장)
  - 모델이 예측 → 전문가(부동산 분석가)가 검토 → 투자자에게 조언
  - 책임 분리 가능

**초기 PoC 전략**
1. 특정 지역 1개(강남), 정책 변수 3개(금리, 규제지수, 세제)만
2. 3개월 오프라인 테스트
3. 50명 베타 투자자로 실제 검증
4. **정책 변화 감시 자동화 (최우선)**

**성공 KPI**
- Precision ≥ 70%
- 월 정책 변화 감시 정확도 ≥ 95%
- 베타 투자자 만족도 ≥ 80%
- 백테스트 수익률 ≥ 벤치마크 + 5%
