##  Chapter 7 체크포인트 — 개발 환경 & 재현성

Q1. VS Code의 원격 개발 기능이 ML 엔지니어에게 왜 필수적인지, GPU 서버 활용 관점에서 설명할 수 있으신가요?

대규모 데이터와 GPU는 원격 서버에 있고, 편집·디버깅은 로컬에서 하고 싶다는 모순을 해결해 주기 때문입니다. VS Code Remote는 원격 서버에 **VS Code Server라는 에이전트**를 설치해, 소스 코드 분석·디버깅 같은 무거운 작업은 서버에서 실행하고 **UI 렌더링만 로컬로** 가져옵니다. 그 결과 대용량 데이터가 있는 GPU 서버에서도 로컬 에디터 수준의 편안함으로 작업할 수 있습니다. ML 작업은 데이터·GPU가 있는 곳에서 코드를 돌려야 하므로, 이 기능은 선택이 아니라 필수입니다.

Q2. 주피터 노트북의 세 가지 문제점(실행 순서, 리팩토링, 버전 관리)을 각각 어떻게 해결하는지 "하이브리드 솔루션"의 관점에서 설명해 보세요.

하이브리드 솔루션의 핵심은 **"탐색·시각화는 노트북에서, 핵심 로직은 `.py` 모듈로 분리"**하고, VS Code 내장 노트북을 쓰는 것입니다.
- **실행 순서의 혼란**: 핵심 로직을 모듈로 빼면 노트북은 짧아지고, 로직은 import해서 항상 동일하게 실행됩니다. "셀 순서 꼬임"으로 인한 "나는 되는데 팀원은 안 됨" 문제가 줄어듭니다.
- **리팩토링의 어려움**: 로직이 `.py`에 있으니 IDE의 "이름 바꾸기(Rename Symbol)" 등 강력한 리팩토링 기능을 그대로 쓸 수 있습니다.
- **버전 관리·테스트**: `.py` 파일은 출력물이 섞이지 않아 Git diff가 깔끔하고 단위 테스트 적용이 쉽습니다.
- 이를 매끄럽게 만드는 장치가 `%load_ext autoreload` / `%autoreload 2`로, 모듈 코드를 수정·저장하면 노트북을 재시작하지 않아도 변경이 자동 반영됩니다.

Q3. "결정적 빌드"가 보장되지 않았을 때, 팀 협업에서 어떤 문제가 발생하는지 경험이나 예시를 떠올려 보실 수 있나요?

결정적 빌드(Deterministic Build)는 내 PC·팀원 PC·클라우드 어디서나 동일한 환경이 재현되는 것을 뜻합니다. 이게 깨지면:
- `pip install torch transformers`를 일주일 뒤 팀원이 실행하면 그 사이 버전이 올라가 **미묘하게 다른 환경**이 생깁니다.
- 새 버전이 기존 코드와 호환되지 않아 **학습 결과가 달라지거나 오류**가 납니다.
- "어제는 됐는데 오늘은 안 되는", "나는 되는데 팀원은 안 되는" 디버깅에 시간을 허비하고, 실험 재현이 불가능해집니다.
- *(예시)* 한 명은 CUDA 11, 다른 한 명은 CUDA 12 환경이라 같은 코드가 한쪽에서만 OOM/에러가 나는 상황.

Q4. `requirements.in`과 `requirements.txt`의 역할 차이를 설명할 수 있으신가요?

- `requirements.in`: **사람이 직접 쓰는** 최상위 의존성 목록으로, 최소한의 제약만 명시합니다(예: `torch`, `transformers`).
- `requirements.txt`: `pip-tools`(`pip-compile`)나 `uv lock`이 `.in`을 입력으로 받아, **상호 호환되는 모든 하위 의존성의 정확한 버전까지 고정(lock)**한 결과 파일입니다.
- 이 `requirements.txt`를 Git에 커밋하면 언제 어디서든 동일한 환경을 복제할 수 있습니다. 즉 `.in`은 "내가 원하는 것", `.txt`는 "그것을 만족시키는 정확한 전체 조합"입니다.



##  Chapter 8 체크포인트 — PyTorch Lightning

Q1. 전통적인 PyTorch 학습 루프 대비 Lightning으로 전환했을 때 사라지는 코드(직접 안 써도 되는 것) 5가지를 나열할 수 있으신가요?

1. **`.to("cuda")` 디바이스 이동 코드** — Trainer가 자동 처리(CPU/GPU 전환 시 코드 수정 불필요).
2. **`for epoch in ...` 학습/검증 루프 자체** — `training_step`/`validation_step`만 정의하면 됨.
3. **메트릭 수동 집계**(`val_loss_sum += ...`) — `self.log(..., on_epoch=True)`가 평균을 자동 계산.
4. **`model.train()` / `model.eval()` / `torch.no_grad()` 전환** — Trainer가 단계별로 자동 처리.
5. **분산 학습·혼합 정밀도·체크포인팅·로깅 보일러플레이트** — `Trainer(devices=4, strategy="ddp", precision="16-mixed", ...)` 파라미터 한 줄로 대체.

Q2. `LightningDataModule`의 `setup` 메서드와 `train_dataloader` 메서드의 역할 차이를 설명할 수 있으신가요? 왜 데이터 분할과 DataLoader 생성을 분리하는 것이 중요한가요?

- `setup(stage)`: 데이터 **다운로드·전처리·train/val/test 분할**을 담당합니다(어떤 데이터를 쓸지 준비). 모든 GPU에서 호출됩니다.
- `train_dataloader()`: 준비된 데이터셋을 받아 **DataLoader 객체를 생성·반환**합니다(어떻게 배치로 흘려보낼지 — `batch_size`, `shuffle`, `num_workers` 등).
- **분리하는 이유**: 데이터 준비(무엇)와 로딩 설정(어떻게)을 나누면, 같은 데이터셋을 다른 배치 설정으로 재사용하기 쉽고, 설정이 한 곳에서 관리되며, **분산 학습 시 각 GPU에 데이터 분할이 자동으로 올바르게 처리**됩니다.

Q3. 이 장에서 배운 `_shared_step` 패턴을 자신의 프로젝트에 적용한다면, 공통 로직과 각 단계(학습/검증/테스트)에서 달라지는 부분은 각각 무엇인가요?

예시 프로젝트: **사진 인기도 점수 예측(연속값 회귀)**.
- **공통 로직(`_shared_step`)**: 배치 언패킹(`x, y = batch`, 여기서 `y`는 연속 인기도 점수), forward(`pred = self(x)`), 회귀 손실 계산(`loss = MSELoss(pred, y)`), 핵심 메트릭(`mae = (pred - y).abs().mean()`) 계산 — 세 단계가 똑같이 쓰는 부분.
- **단계별로 달라지는 부분**:
  - `training_step`: loss를 **반환**(역전파 대상), `on_step=True`로 스텝 단위 로깅, backward/optimizer는 Lightning이 처리.
  - `validation_step`: loss 반환 불필요, `prog_bar=True`로 `val_loss`·`val_mae` 표시, 그래디언트 비활성(자동).
  - `test_step`: 최종 평가 지표만 로깅(`test_mae`, `test_rmse`).

Q4. `overfit_batches=1` 테스트가 실패했을 때 의심해야 할 원인 3가지와, 각각의 디버깅 방법을 설명할 수 있으신가요?

`overfit_batches=1`은 단 1개 배치를 모델이 완벽히 암기(Loss→0)하는지 보는 스모크 테스트입니다. Loss가 0으로 수렴하지 않으면:
1. **그래디언트 계산이 깨져 가중치가 업데이트되지 않음** → `loss.requires_grad`/그래프 연결 확인, `optimizer`에 올바른 `model.parameters()`가 들어갔는지, 중간에 `.detach()`나 `torch.no_grad()`가 잘못 끼지 않았는지 점검.
2. **레이블과 데이터 순서가 뒤섞임(셔플링 오류)** → DataLoader에서 x와 y의 매칭, `random_split`/인덱싱 로직 확인, 한 배치를 직접 출력해 입력-정답 대응 검증.
3. **수치적 불안정성으로 NaN 발생** → loss/그래디언트에 NaN이 뜨는지 확인, 학습률을 낮추거나 `gradient_clip_val` 적용, 혼합 정밀도 사용 중이면 잠시 끄고 비교.

Q5. 8.13의 전체 코드를 여러분의 실제 프로젝트에 맞게 수정한다면, `LitClassifier.__init__`과 `MyDataModule.setup`에서 각각 무엇을 바꿔야 하는지 구체적으로 떠올려 보세요. (예시 답안 — 사진 인기도 점수 예측, 회귀)

- **`LitClassifier.__init__`**(회귀용으로 개명하면 `LitRegressor`): 모델 아키텍처(`nn.Sequential` → 이미지 입력용 CNN/사전학습 백본), **출력 차원을 `num_classes` 대신 1**(연속 점수 1개)로, 손실 함수(`CrossEntropyLoss` → **`nn.MSELoss`**, 이상치에 강하게 하려면 `SmoothL1Loss`), 하이퍼파라미터(`hidden_dim`, `lr`, dropout) 조정.
- **`MyDataModule.setup`**: 가상 데이터(`torch.randn`) 대신 **실제 사진 데이터 로딩**(이미지 파일/DB의 URL→로드), 이미지 정규화·리사이즈 transform 추가, **타깃 `y`를 정수 클래스가 아닌 연속 인기도 점수(float)**로, 실제 크기에 맞는 train/val/test 분할.

##  Chapter 9 체크포인트 — GPU & 인프라

Q1. GPU 선택의 3대 지표(메모리 대역폭, 연산 속도, 인터커넥트) 중 분산 학습에서 가장 중요한 것은 무엇이며, 그 이유를 "고속도로와 톨게이트" 비유로 설명할 수 있으신가요?

분산 학습에서는 **인터커넥트(Interconnect, GPU 간 통신 속도)**가 가장 중요합니다. 분산 학습은 매 스텝마다 GPU들이 그래디언트를 서로 교환(평균화)해야 하므로, 이 통신이 느리면 전체 학습 속도가 거기서 결정됩니다. **NVLink**가 있으면 GPU끼리 직접 초고속 통신이 가능해 GPU 수에 비례하는(선형적) 성능 향상을 얻지만, 소비자용 카드(RTX)는 NVLink가 없어 PCIe를 거치므로 GPU 4개를 써도 3배 정도에 그칩니다.
- **고속도로/톨게이트 비유**: 메모리 대역폭이 "메모리→연산장치 사이 톨게이트"라면, 인터커넥트는 "GPU와 GPU를 잇는 고속도로"입니다. 연산장치(차)가 아무리 빨라도 GPU 간 고속도로가 좁으면, 그래디언트 교환에서 정체가 생겨 전체가 느려집니다.

Q2. "시간당 비용"이 아니라 "실험당 비용"으로 GPU를 평가해야 하는 이유를 표의 숫자 예시를 활용하여 설명할 수 있으신가요?

시간당 대여료만 보고 싼 GPU를 고르면, 느려서 학습이 오래 걸려 총비용이 오히려 커집니다. 봐야 할 것은 **하나의 실험을 끝내는 데 드는 총비용(실험당 비용 = 시간당 단가 × 소요 시간)**입니다. 노트북 예시에서는 동일한 실험인데도 GPU 선택에 따라 **총비용이 약 7배** 차이가 났습니다. 성능 좋은 GPU는 시간당 비싸도 학습 시간을 크게 줄여, 총 프로젝트 비용과 엔지니어 대기 시간을 모두 절감합니다. → 결론: **"가장 저렴한 클라우드 업체에서 가장 성능 좋은 GPU를 빌려 짧게 끝내는 것"**이 가장 경제적입니다.

Q3. 스팟 인스턴스를 안전하게 사용하기 위해 반드시 갖춰야 할 전제 조건은 무엇인가요?

**체크포인팅 자동화**가 필수 전제 조건입니다. 스팟 인스턴스는 남는 GPU를 70~90% 할인가에 주지만, 수요가 오르면 **언제든 회수**될 수 있습니다. 회수 시점에 진행 상황을 잃지 않으려면 검증 성능 기준으로 체크포인트를 자동 저장하고, 재시작 시 마지막 체크포인트에서 이어 학습할 수 있어야 합니다. PyTorch Lightning은 이를 기본 지원하므로(옵티마이저·에포크·스케줄러 상태까지 저장), **Lightning을 쓰는 것 자체가 스팟 인스턴스 기반 비용 최적화의 전제**가 됩니다.

Q4. 여러분이 실습에서 진행한 실험 중, W&B가 있었다면 어떤 점이 편리했을지 구체적으로 떠올려 보실 수 있나요? (예시 답안 — 사진 인기도 점수 예측, 회귀)

- 여러 학습률·배치 사이즈로 돌린 인기도 예측 실험들을 노트북 메모 대신 **대시보드에서 한눈에 비교**하고, 학습률↔검증 MAE 상관관계를 시각적으로 분석.
- "그때 검증 RMSE가 제일 낮았던 하이퍼파라미터"를 `config` 자동 기록으로 정확히 재현.
- GPU 사용률·메모리 같은 **시스템 메트릭 자동 수집**으로 데이터 로딩 병목/OOM 원인 파악.
- 학습 곡선을 실시간으로 보며 손실이 발산하는 실험을 일찍 중단해 GPU 시간 절약.

##  Chapter 10 체크포인트 — 데이터 스토리지

Q1. 스토리지 계층 구조의 지연 시간 차이가 `DataLoader`의 `num_workers` 설정에 어떤 영향을 미치는지 설명할 수 있으신가요?

스토리지마다 접근 지연이 천문학적으로 다릅니다(CPU 캐시 ≪ RAM ≪ NVMe SSD ≪ 네트워크/객체 저장소). 학습 데이터는 결국 **GPU 옆 로컬 NVMe SSD**에 있어야 하지만, 디스크 읽기조차 GPU 연산에 비하면 느립니다. `DataLoader`의 `num_workers`를 늘리면 여러 워커 프로세스가 **다음 배치를 미리(prefetch) 읽어** 메모리에 올려두므로, GPU가 현재 배치를 연산하는 동안 다음 배치가 준비되어 GPU가 데이터를 기다리며 놀지 않습니다. 즉 스토리지 지연이 클수록 prefetch(충분한 `num_workers`)의 효과가 큽니다. 최적값은 보통 **CPU 코어 수의 절반~전체** 사이이며 실험적으로 조정합니다.

Q2. "이진 데이터는 S3에, URL만 DB에"라는 원칙의 이유를 설명할 수 있으신가요? 이 원칙을 어겼을 때 어떤 문제가 발생하나요?

이미지·오디오·비디오 같은 이진 데이터는 **객체 저장소(S3)**에 올리고, 데이터베이스에는 그 파일의 **URL(주소)만** 저장하라는 원칙입니다. DB에 이진 데이터를 직접 넣으면 **DB 성능이 급격히 저하되고, 백업·복제가 어려워집니다**. DB는 구조화된 데이터의 빠른 조회·쓰기에 최적화돼 있는데, 큰 바이너리(BLOB)를 넣으면 그 강점을 잃고 무거워집니다. URL만 두면 DB는 가볍게 유지되고, 대용량 파일은 확장성 좋은 S3가 담당하게 됩니다.

Q3. OLTP와 OLAP의 차이를 "행 지향 vs 열 지향"의 관점에서, 각각 어떤 쿼리에 적합한지 예시와 함께 설명할 수 있으신가요?

- **OLTP (행 지향)**: 한 레코드를 통째로 빠르게 읽고 쓰는 데 최적. *예) "사용자 A의 모든 주문을 조회하라"* 처럼 특정 행 단위 트랜잭션. 도구: **Postgres**(권장, JSON 쿼리 지원), **SQLite**(파일 하나, 프로토타이핑).
- **OLAP (열 지향)**: 특정 컬럼만 모아 대량 집계·분석하는 데 최적. *예) "지난 30일 전체 이미지의 평균 해상도를 계산하라"*. 열 단위 저장이라 필요한 컬럼만 읽으면 되어 분석이 빠르고 압축률도 높음. 도구: BigQuery, Snowflake, Databricks(레이크하우스).
- 한 줄 요약: **특정 레코드 조회·갱신 = OLTP, 대량 컬럼 집계·분석 = OLAP.**

##  Chapter 11 체크포인트 — 데이터 레이블링

Q1. 레이블링을 최소화하는 4가지 전략(자기주도 학습, 증강, 합성 데이터, 사용자 피드백)을 각각 한 문장으로 요약하고, 자신의 프로젝트에 적용 가능한 것을 골라보실 수 있나요?

- **자기주도 학습(Self-supervised)**: 데이터 자체의 구조를 정답으로 삼아(다음 토큰 예측, 마스킹 복원, 대조 학습) 레이블 없이 학습.
- **데이터 증강(Augmentation)**: 본질적 의미는 유지한 채 표면적 특성만 바꿔(회전·크롭·역번역·잡음 추가 등) 한 데이터를 여러 학습 데이터로 확장.
- **합성 데이터(Synthetic)**: 알고리즘·생성 모델(특히 LLM)로 정답을 알고 있는 데이터를 직접 생성해 레이블링 비용을 0으로.
- **사용자 피드백→레이블**: 클릭·스킵·수정·평점 같은 사용자 행동을 암묵적 레이블로 전환(데이터 플라이휠).
- *(예시 선택 — 사진 인기도 점수 예측, 회귀)* 사용자 피드백(좋아요·조회수·체류시간)이 그대로 연속 인기도 점수 레이블이 되므로 **사용자 피드백→레이블** 전략이 가장 잘 맞고, **이미지 증강**으로 데이터를 추가 확보할 수 있습니다.

Q2. 수동 레이블링의 5단계 프로세스 중 "골드 표준 데이터셋"은 왜 필요한가요? 이것 없이 외주를 맡기면 어떤 문제가 생기나요?

골드 표준(Gold Standard)은 **엔지니어가 직접 레이블링한 소량(보통 200~500개)의 기준 데이터셋**으로, 레이블러의 작업 결과를 여기에 비교해 **품질을 객관적으로 평가**하는 잣대입니다. 이것이 없으면:
- 외주 결과가 맞는지 틀렸는지 판단할 기준이 없어 **품질 관리가 불가능**합니다.
- 모호한 케이스에 대해 레이블러마다 다른 기준으로 작업해도 걸러내지 못합니다.
- 결과적으로 비용은 많이 들면서 품질이 낮은, 신뢰할 수 없는 데이터셋이 만들어집니다.
- (보완) 평가자 간 일치도(Cohen's/Fleiss' Kappa) 측정과 함께 쓰면 가이드라인의 모호함도 잡아낼 수 있습니다.

Q3. 약지도 학습이 수동 레이블링 대비 갖는 가장 큰 장점을 "유지보수" 관점에서 설명해 보세요. 레이블 체계가 변경되었을 때 각각 어떤 일이 벌어지나요?

가장 큰 장점은 **유지보수성**입니다.
- **수동 레이블링**: 레이블 체계가 바뀌면(예: "긍정/부정" → "긍정/중립/부정") **모든 데이터를 처음부터 다시 레이블링**해야 합니다 — 막대한 비용·시간 재발생.
- **약지도 학습(Snorkel 등)**: 휴리스틱을 코드로 만든 **레이블링 함수(LF)만 수정하고 다시 실행**하면 수백만 개 레이블을 즉시 갱신할 수 있습니다. Snorkel은 여러 LF가 충돌할 때 각 함수의 정확도·상관관계를 학습해 노이즈가 적은 최종 레이블을 만들어 줍니다.

Q4. LLM을 이용한 합성 데이터 생성이 효과적인 상황과 주의해야 할 점은 무엇인가요?

- **효과적인 상황**: 대규모 Fine-tuning 데이터셋을 빠르게 구축할 때(2026년 현재 핵심 전략). 예) "고객 문의에 대한 친절한 응답 1000개를 생성하라"는 프롬프트로 GPT-4o 등에 학습 데이터를 만들게 함. 생성 시점에 정답을 알고 있어 레이블링 비용이 사실상 0.
- **주의할 점**: **합성 데이터의 품질을 검증하는 단계가 반드시 필요**합니다. LLM이 만든 데이터는 사실 오류·편향·다양성 부족·실제 분포와의 괴리가 있을 수 있으므로, 그대로 학습에 넣지 말고 필터링·검수를 거쳐야 합니다.

##  Chapter 12 체크포인트 — 데이터 버전 관리 & 워크플로우

Q1. 데이터 버전 관리의 4단계 중 자신의 현재 프로젝트는 어느 레벨에 해당하나요? 한 단계 올리려면 구체적으로 무엇을 해야 하나요? (예시 답안)

4단계: **Level 0 무관리 → Level 1 스냅샷 → Level 2 코드로서의 데이터(추천) → Level 3 전문 도구(DVC)**.
- *(예시 — 사진 인기도 예측 프로젝트)* 사진과 인기도 점수를 그냥 로컬/S3에 두고 어떤 데이터로 학습했는지 기록이 없다면 **Level 0**입니다. 가장 중요한 건 **Level 0에서 벗어나는 것**.
- **한 단계 올리기(→ Level 2)**: 사진(이진 데이터)은 S3에 두고, 그 URL + 인기도 점수를 담은 메타데이터(Parquet/JSON) "장부"를 만들어 **Git LFS로 버전 관리**. 그러면 장부를 과거 버전으로 되돌리면 그 시점 데이터셋이 복원됩니다.

Q2. "코드 + 데이터 = 모델"이라는 공식에서, 데이터 버전 관리 없이 모델을 롤백하려 할 때 어떤 문제가 발생하는지 구체적인 시나리오를 그려보실 수 있나요?

ML에서는 코드가 같아도 데이터가 다르면 다른 모델이 나옵니다. 시나리오: **배포된 모델 성능이 갑자기 하락 → 코드를 지난주 버전으로 롤백 → 그래도 성능이 복구되지 않음.** 원인은 그사이 데이터셋이 업데이트됐기 때문입니다. 그런데 데이터가 버전 관리되지 않았다면 **"지난주의 정확한 데이터 상태"를 재현할 방법이 없어** 문제의 원인 분리도, 정상 모델 복원도 불가능합니다. 즉 코드만 버전 관리해서는 ML 모델을 온전히 롤백할 수 없습니다.

Q3. Level 2("코드로서의 데이터")의 "장부" 비유를 자신의 언어로 다시 설명할 수 있으신가요? (예시 답안)

수천 개의 사진 원본 파일을 일일이 Git에 넣어 관리하는 대신, 그 파일들의 **주소(S3 URL)와 인기도 점수가 적힌 "장부"(메타데이터 파일) 하나만 Git으로 관리**한다는 뜻입니다. 실제 무거운 사진은 S3에 그대로 두고, 가벼운 장부만 버전 관리하는 것이죠. 장부를 지난주 커밋으로 되돌리면, 그 장부가 가리키는 대로 **지난주의 데이터셋이 자동으로 복원**됩니다. 은행 통장처럼 "돈(원본 파일) 자체"가 아니라 "거래 내역(어떤 파일을 썼는지)"을 기록하는 셈입니다.

Q4. 워크플로우 자동화가 필요해지는 시점은 언제인가요? "단순한 파이썬 스크립트"로 충분한 경우와, Airflow 같은 전문 도구가 필요한 경우를 구분할 수 있으신가요?

- **필요해지는 시점**: 실험 단계를 넘어 서비스로 가서, **매일/매시간 반복되는 데이터 처리**가 생기고, 작업들에 **순서·의존성**이 있어 앞 단계가 실패하면 뒤 단계를 막아야 할 때(예: 메타데이터 추출 → 특징 생성 → 스타일 분석 → 모델 재학습). 이런 의존성은 DAG(유향 비순환 그래프)로 관리합니다.
- **단순 파이썬 스크립트로 충분**: 작업이 단발성이거나, 단일 머신(예: 32코어 PC)에서 끝나고, 실패 재시도·스케줄링·모니터링이 크게 필요 없을 때. 노트북의 "하둡 26분 vs 유닉스 명령 70초" 사례처럼 **오버 엔지니어링을 경계**해야 합니다.
- **Airflow 등 전문 도구가 필요**: 작업이 많고 의존성이 복잡하며, **실패 자동 재시도·스케줄링·대시보드 모니터링**이 필요하고 여러 시스템에 걸쳐 안정적으로 돌려야 할 때(Airflow=업계 표준, Prefect=더 직관적, Dagster=데이터 흐름 중심).

##  Day 2 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기


1. 환경 점검
재현 가능한 환경을 위해서는 결정적 빌드가 보장돼야 합니다. 전달에 필요한 파일: ① 뼈대(Python/CUDA 버전) — `environment.yml`(Conda) 또는 `uv` 설정, ② 의존성 잠금 — `requirements.in`(최상위) + 잠긴 `requirements.txt`, ③ 자동화 — `make install` 한 줄로 환경을 세우는 `Makefile`. 팀원에게는 "이 레포 클론 후 `make install` 하나만 실행하세요"가 가능해야 합니다.

2. 코드 리팩토링 계획
기존 PyTorch 인기도 예측(회귀) 학습 코드를 Lightning으로 분리:
- `LightningModule`로 → 모델 정의(`__init__`), `forward`, 그리고 `training_step`/`validation_step`/`configure_optimizers`.
  - `training_step`: 배치 forward + 회귀 손실(`MSELoss`) 계산 후 loss 반환(+ `self.log("train_loss")`).
  - `validation_step`: forward + `val_loss`(MSE)/`val_mae` 계산, `on_epoch=True, prog_bar=True`로 로깅(loss 반환 없음).
  - `configure_optimizers`: AdamW + CosineAnnealingLR 등 옵티마이저·스케줄러 반환.
- `Trainer` 설정으로 → `accelerator`, `devices`, `strategy="ddp"`, `precision="16-mixed"`, `max_epochs`, `gradient_clip_val`, 그리고 `ModelCheckpoint`(monitor="val_mae")·`EarlyStopping`·`LearningRateMonitor` 콜백, `WandbLogger`.

3. 인프라 설계 (예시)
- **GPU**: 프로토타이핑은 자체 워크스테이션(RTX 4090) 또는 GPU 전문 스타트업(Lambda/RunPod). 대규모·다GPU 학습은 H100급 클라우드(인터커넥트/NVLink 고려).
- **클라우드**: 실험·가성비는 Lambda Labs/RunPod/Vast.ai(대형 클라우드의 1/2~1/3), 엔터프라이즈 SLA·보안 필요 시 AWS/GCP/Azure.
- **실험 관리**: W&B(대시보드·시스템 메트릭 자동 수집). 데이터 외부 반출 불가 환경이면 MLflow 자체 호스팅.
- **비용 절감**: 스팟 인스턴스 + (Lightning) 체크포인팅 자동화.

4. 데이터 전략 (예시)
- **데이터 확보**: 서비스 로그/DB에서 사진 메타데이터 추출 + 사용자 피드백(좋아요·조회수·체류시간)을 연속 인기도 점수 레이블로 활용(플라이휠).
- **레이블링 최소화**: 사용자 피드백→레이블 + 이미지 증강. 추가 레이블이 필요하면 능동적 학습으로 불확실성 높은 샘플만 골라 레이블링.
- **데이터 버전 관리**: 최소 **Level 2(코드로서의 데이터, Git LFS로 메타데이터 장부 관리)**부터 시작. 파이프라인이 복잡해지면 Level 3(DVC) 검토.

5. 비용 시뮬레이션 (예시)
- 1 실험 ≈ 20 에포크, 데이터셋 규모·모델 크기로 GPU-시간 추산(예: A100 1대 × 6시간 = 6 GPU-시간).
- **시간당 관점**: 싼 GPU(저단가·저속)는 시간당은 싸지만 학습이 길어짐. **실험당 관점**: 고성능 GPU는 시간당 비싸도 학습이 짧아 총비용이 낮아질 수 있음(노트북 예시 최대 7배 차이).
- **스팟 조건**: Lightning 체크포인팅이 자동 저장되도록 구성돼 있으면 스팟 인스턴스로 70~90% 절감 가능. 회수돼도 마지막 체크포인트에서 재개.
