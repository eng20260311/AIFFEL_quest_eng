# Full Stack Deep Learning — Day 3 체크포인트 문제 & 답안


## ✅ Chapter 13 체크포인트 — ML 시스템의 테스트 전략

Q1. ML 테스트가 "다크 소울"이라 불리는 이유를 전통 소프트웨어와 비교하여 3가지 관점에서 설명할 수 있으신가요?

1. **정답의 성격**: 전통 SW는 테스트를 통과하면 "맞다"고 간주합니다. 그러나 **ML 모델은 항상 어느 정도 틀려 있습니다.** 0이 아닌 손실(non-zero loss)은 "부분적 실패"이므로, ML 테스트는 "맞느냐 틀리느냐"가 아니라 **"얼마나 틀리느냐가 허용 범위 안인가"**를 판단합니다.
2. **결정론 vs 확률론**: 전통 SW는 결정론적이라 같은 입력에 항상 같은 출력이 나오지만, ML은 확률적이라 부동소수점 오차·데이터 셔플링으로 결과가 미세하게 달라집니다. 그래서 '값이 정확히 일치하는가'보다 **'통계적 분포가 허용 범위 내인가'**를 측정해야 합니다.
3. **데이터가 새로운 코드**: 코드 버그는 프로그램을 죽게 만들지만, **데이터 오류는 모델이 조용히 잘못된 것을 학습**하게 만들어 더 위험합니다. 검증 대상이 코드뿐 아니라 데이터까지 확장됩니다.

Q2. 테스트 수트를 "분류기"로 보았을 때, 오탐(False Alarm)이 왜 위험한지 실제 사례를 들어 설명할 수 있으신가요?

테스트 수트는 "이 커밋에 버그가 있는가?"를 판정하는 분류기이고, 핵심 트레이드오프는 **탐지(Detection) vs 오탐(False Alarm)**입니다. 오탐이 많으면 테스트의 신뢰가 무너집니다. 전형적인 위험 사례: 테스트가 실패했을 때 **코드를 고치는 대신 테스트 코드 자체를 수정해서 통과**시키는 상황 — 이러면 테스트가 더 이상 버그를 잡지 못하는 장식이 됩니다. 그래서 100% 커버리지가 목표가 되어선 안 되고, 테스트는 **'증명'이 아니라 '위험 관리'**의 수단입니다. (단, 자율주행·의료·금융 같은 고위험 시스템은 규제상 훨씬 엄격한 테스트가 필요합니다.)

Q3. 암기 테스트(`overfit_batches=1`)가 실패했을 때 의심해야 할 원인 5가지를 나열하고, 각각의 디버깅 방법을 떠올릴 수 있으신가요?

암기 테스트는 `DataLoader → Model → Loss → Optimizer → GPU` 배관이 모두 연결됐는지 증명합니다. 단 1개 배치도 암기(Loss→0)하지 못하면:
1. **그래디언트 계산 오류**(특정 레이어에 그래디언트 미전파) → `.requires_grad` 확인, 연산 그래프가 중간에 끊겼는지(`.detach()`/`no_grad`) 점검.
2. **데이터 셔플링 오류**(x와 y 순서가 뒤섞임) → 한 배치를 직접 출력해 입력-정답 대응 검증.
3. **전처리 버그**(정규화 부호 오류 등, 평균을 빼야 하는데 더함) → 전처리 전후 값 분포 확인.
4. **수치적 문제**(그래디언트 폭주/소실로 NaN·Inf) → loss/그래디언트 NaN 확인, `gradient_clip_val`·학습률 조정.
5. **옵티마이저 설정 오류**(학습률 0, 잘못된 파라미터 그룹 전달) → optimizer에 올바른 `model.parameters()`가 들어갔는지, lr 값 확인.
- 추가 원칙: 암기 테스트 시에는 **Dropout·Data Augmentation 등 모든 규제를 끄세요**(의도적 오버피팅이므로). 10분 이내로 유지하세요.

Q4. 데이터 기댓값 테스트에서 "느슨한 경계" 원칙이 왜 중요한지, 경계를 너무 엄격하게 잡으면 어떤 문제가 발생하는지 설명해 보세요.

경계를 너무 엄격하게 잡으면 **정상 데이터인데도 테스트가 실패(오탐)**합니다. 예: 사람 키가 보통 4~8피트라고 그 범위로 잡으면, 정상 범주의 데이터까지 알람을 울립니다. 대신 **"키는 음수일 수 없고 30피트를 넘을 수 없다"**처럼 느슨하게 잡으면, 인치를 피트로 잘못 입력한 것 같은 **진짜 불이 난 상황(단위 오류)**은 잡으면서 불필요한 알람은 줄입니다. 스모크 테스트는 "모든 버그"가 아니라 "시스템에 불이 났는지"를 보는 것이므로 느슨하게 시작하고, 데이터 이해가 깊어지면 통계적 범위(예: 99%가 평균±3σ 이내) 같은 더 정교한 기댓값으로 **점진적으로 강화**합니다.

Q5. 행동 테스트의 "불변성 테스트"와 "방향성 테스트"의 차이를 자신의 프로젝트에 적용하여 각각 1개씩 예시를 만들어 보실 수 있나요? (예시 답안 — 한국어 뉴스 분류)

- **불변성 테스트(Invariance)**: 입력을 바꿔도 **출력이 같아야** 하는 경우. *예) "삼성전자 새 반도체 공장 착공" → 쉼표·띄어쓰기·어미를 살짝 바꿔도 카테고리는 그대로 'IT과학'이어야 함.* 깨지면 모델이 표면적 형식에 과민하다는 신호.
- **방향성 테스트(Directional)**: 입력을 바꾸면 출력이 **특정 방향으로 변해야** 하는 경우. *예) "코스피 3000선 회복"의 핵심 경제 키워드를 IT 키워드로 교체하면, 예측 카테고리가 '경제'에서 'IT과학' 쪽으로 이동해야 함.* (감성 분석이라면 "편리합니다 → 편리하지 않습니다"로 바꾸면 점수가 하락해야 함.)

## ✅ Chapter 14 체크포인트 — 모델 트러블슈팅 3단계

Q1. "Make it Run → Make it Fast → Make it Right" 순서에서, 왜 ML에서는 "Fast"가 "Right"보다 먼저 와야 하는지 설명할 수 있으신가요?

ML 모델은 항상 어느 정도 틀려 있으므로 **"올바르게(Right)"는 끝이 없는 여정**입니다. 성능을 끌어올리려면 더 많은 실험을 돌려야 하는데, 그러려면 **실험 주기를 단축하는 "빠르게(Fast)"가 먼저** 확보되어야 합니다. **하루에 1번 실험하는 팀과 10번 실험하는 팀 사이에는 넘을 수 없는 생산성 차이**가 있습니다. 그래서 전통 SW의 "작동→올바르게→빠르게" 순서를 ML에서는 "작동→빠르게→올바르게"로 바꿉니다.

Q2. OOM 오류를 해결하는 4단계 전략을 순서대로 말할 수 있으신가요? Adam이 파라미터의 3~4배 메모리를 쓰는 이유는 무엇인가요?

OOM 대응 4단계(순서대로):
1. **정밀도 낮추기** — `precision="16-mixed"`. 메모리 거의 절반 + 속도↑("공짜 점심").
2. **배치 사이즈 줄이기** — 직관적이지만 너무 작으면 학습 불안정.
3. **그래디언트 축적** — `accumulate_grad_batches=4`. 물리적으로 작은 배치, 수학적으로 큰 배치 효과.
4. **그래디언트 체크포인팅** — 활성화 값을 저장하지 않고 역전파 때 재계산(메모리를 속도와 교환).
- **Adam이 3~4배 메모리를 쓰는 이유**: 파라미터마다 **모멘텀(Momentum)과 분산(Variance)** 두 상태값을 저장(2P) + 혼합 정밀도 학습 시 **FP32 마스터 가중치**(1P)가 추가됩니다. 그래서 옵티마이저만으로 파라미터 크기의 3~4배가 필요합니다. 모델이 GPU 메모리의 1/4도 안 되는데 OOM이면 옵티마이저 상태를 의심하세요.

Q3. 프로파일링 결과에서 `get_train_batch`가 전체 시간의 60%를 차지한다면, 어떤 최적화를 우선 시도하시겠어요? 반대로 `training_step`이 90%라면요?

암달의 법칙에 따라 **비중이 가장 큰 병목부터** 공략합니다.
- **`get_train_batch` 60% (데이터 로딩 병목, "데이터 굶주림")**: ① `num_workers` 증가(CPU 코어 절반~전체) ② `persistent_workers=True` ③ `pin_memory=True` ④ 데이터를 NVMe SSD에 배치 ⑤ 무거운 전처리 사전 캐싱(`.pt`/`.arrow`) ⑥ GPU 기반 전처리(NVIDIA DALI). GPU를 바꾸기 전에 데이터 파이프라인부터 고칩니다.
- **`training_step` 90% (모델 연산 병목)**: 혼합 정밀도(`16-mixed`), `torch.compile(model)`(커널 퓨전 20~50%↑), 모델 경량화를 시도합니다.

Q4. 스케일링 법칙의 "작은 실험 → 직선 외삽 → 필요 자원 추산" 흐름을 자신의 언어로 설명하고, 이것이 비즈니스적으로 어떤 가치를 주는지 설명해 보세요.

모델 성능(Loss)은 **연산 예산·데이터셋 크기·파라미터 수**에 따라 거듭제곱 법칙으로 향상되며, 로그-로그 스케일에서 직선으로 나타납니다. 실전 흐름:
1. **작은 규모 실험 3~5개** — 파라미터/데이터를 점진적으로 늘리며 각 최종 Loss를 기록.
2. **로그-로그 차트에 점을 찍고 직선 회귀** — x축 자원, y축 Loss.
3. **직선을 연장(외삽)해 필요 자원 추산** — "목표 Loss에 도달하려면 데이터 10배, GPU 시간 5배"라는 구체적 숫자를 얻음.
- **비즈니스 가치**: "실험을 10배 돌리면 성능이 X% 향상될까?"에 **데이터 기반으로 답**할 수 있습니다. 학습을 언제 멈출지, 모델을 얼마나 키울지, 비용이 얼마나 들지를 미리 예측해 자원 투자를 합리적으로 결정합니다(선도 팀들이 쓰는 방식). 단, Chinchilla 연구처럼 파라미터와 데이터를 **균형 있게** 늘려야 합니다.

Q5. 성능 저하 진단표(오버피팅/언더피팅/분포 변화)에서, 자신의 최근 프로젝트가 어떤 상황이었는지 분석하고 적절한 처방을 매칭해 보세요. (예시 답안)

성능이 안 나올 때 첫 번째 할 일은 **train_loss와 val_loss 비교**입니다.
- **오버피팅**(train_loss는 낮은데 val_loss가 높음) → 처방: **데이터 더 모으기**, 데이터 증강, 규제(Dropout/Weight Decay) 강화.
- **언더피팅**(train·val 둘 다 높음) → 처방: **모델 크기 키우기**, 더 오래/높은 학습률로 학습, 아키텍처 개선.
- **분포 변화**(학습/검증 분포가 다름) → 처방: **둘 다** — 데이터 재수집·분할 점검 + 모델 일반화.
- *(예시)* 뉴스 분류에서 train F1은 0.95인데 val F1이 0.80이라면 오버피팅 → 데이터 증강·`max_length` 조정·Dropout 강화로 대응.

## ✅ Chapter 15 체크포인트 — LLM 시대의 평가와 모니터링

Q1. LLM 기반 시스템을 Accuracy만으로 평가할 수 없는 이유를 설명하고, 추가로 필요한 평가 차원을 5가지 나열할 수 있으신가요?

LLM 기반 시스템(RAG·Agent·챗봇)은 "정답/오답"의 단일 숫자로 품질을 포착하기 어렵습니다. "정확하지만 딱딱한 답변"과 "자연스럽지만 환각이 섞인 답변" 중 무엇이 나은지는 비즈니스 맥락에 따라 다르고, 하나의 숫자로 요약하면 **어느 차원이 약한지** 알 수 없습니다. 추가로 필요한 평가 차원:
1. **유창성(Fluency)** — 답변이 자연스러운가
2. **사실성/충실성(Faithfulness)** — 환각 없이 근거에 부합하는가
3. **스타일/톤(Tone)** — 톤이 적절한가
4. **근거 참조(Attribution)** — (RAG) 근거 문서를 정확히 참조하는가
5. **의도 이해(Intent Understanding)** — 사용자 의도를 정확히 파악했는가
6. **안전성(Safety)** — 유해·편향 내용이 없는가

Q2. LLM-as-a-Judge의 장점과 주의할 한계(편향)를 각각 설명하고, 편향을 완화하는 방법을 하나 제안해 보세요.

- **장점**: 강력한 LLM(GPT-4o·Claude)을 평가자로 써서 평가 기준을 프롬프트로 정의하면, **인간 평가보다 10~100배 빠르고 저렴**하며 인간 판단과의 상관관계가 **0.7~0.9**로 높습니다.
- **한계(편향)**: 평가 LLM 자체의 편향, 특히 **길이 편향**(긴 답변에 더 높은 점수를 주는 경향)에 유의해야 합니다.
- **완화 방법**: 평가 프롬프트에 **"길이에 관계없이 핵심만 평가하라"**는 지시를 넣고, 주기적으로 소량(50~100개)의 **인간 평가로 교정(Calibration)**합니다.

Q3. 입력 드리프트, 출력 드리프트, 성능 드리프트의 차이를 각각 한 문장으로 설명하고, 자신의 프로젝트에서 가장 가능성 높은 드리프트 유형은 무엇인지 분석해 보세요. (예시 답안)

- **입력 드리프트(Input/Feature Drift)**: 모델에 들어오는 데이터의 통계적 분포가 학습 시점과 달라지는 것(계절·인구통계 변화 등).
- **출력 드리프트(Prediction Drift)**: 모델의 예측 분포가 변하는 것(예: 갑자기 특정 클래스를 과도 예측).
- **성능 드리프트(Performance/Concept Drift)**: 실제 정답 대비 성능이 시간에 따라 변하는 것(가장 확실하나 Ground Truth 확보에 시간이 걸림).
- *(예시 — 뉴스 분류)* 새로운 이슈·신조어·새 카테고리 주제가 계속 등장하므로 **입력 드리프트**가 가장 가능성이 높습니다. 주요 입력 피처(어휘 분포)를 KS 검정으로 학습 시점과 비교해 감지합니다.

Q4. "모델은 시간이 지나면 썩는다"는 말의 의미를 코로나19 같은 구체적 사례로 설명할 수 있으신가요? 이를 방지하기 위해 어떤 시스템이 필요한가요?

전통 SW는 코드를 안 바꾸면 동일하게 작동하지만, **ML 모델은 외부 세계가 변하면 코드를 한 줄도 안 바꿔도 성능이 저하**됩니다(데이터 드리프트). 사례: **코로나19 팬데믹 이후 소비자 행동 패턴이 급변**해, 팬데믹 이전 데이터로 학습한 추천·수요예측 모델이 하루아침에 쓸모없어졌습니다. 이를 방지하려면 **배포 후 모니터링 시스템**이 필요합니다 — 입력/출력/성능 분포를 학습 시점과 비교(KL-Divergence·KS 검정), **임계값을 설정**하고 넘으면 **Slack/이메일 자동 알림**, 필요 시 재학습 파이프라인 트리거. 단, 알림이 울리면 "진짜 세상이 변한 것인가, 우리 파이프라인이 깨진 것인가"를 먼저 구분해야 합니다.
